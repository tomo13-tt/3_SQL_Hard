# 課題3 模範解説

## リファクタリング方針

課題2の指標定義を変えず、粒度と責務をCTE名から追える構造へ変更しました。明細系、注文系、最終粒度という3本の境界を明示しています。

## 変更したCTE構成

| 構成 | 粒度 | 責務 |
|---|---|---|
| `eligible_order` | 注文 | 対象注文、顧客、配送特徴 |
| `item_detail` | 注文明細 | 商品、カテゴリ、販売者属性 |
| `payment_order` | 注文 | 決済集約 |
| `review_order` | 注文 | レビュー集約 |
| `order_item_control` | 注文 | 明細数と金額のコントロール |
| `order_category_item` | 注文×カテゴリ | 決済配賦の分子 |
| `order_category_experience` | 注文×カテゴリ | 注文系特徴と配賦決済額 |
| `category_item_month` | 顧客×月×カテゴリ | 明細系指標 |
| `category_order_month` | 顧客×月×カテゴリ | 注文系指標 |
| `category_month_feature` | 顧客×月×カテゴリ | 明細系と注文系の統合 |
| `customer_order` | 注文 | カテゴリ非依存の顧客月次入力 |
| `customer_month_feature` | 顧客×月 | 月次指標 |
| `final_feature` | 顧客×月×カテゴリ | 構成比とリスク区分 |

## 主な改善

- CTE名に粒度を表す語を含めました。
- 顧客属性の結合を `eligible_order` にまとめ、同じ結合の反復を減らしました。
- 課題2の `order_category_items` にあった、決済配賦で使わない商品属性集計を除きました。
- 明細を分母とする指標と注文を分母とする指標を別CTEへ分離しました。
- `customer_month_feature` はカテゴリ集計から作らず、注文粒度から作りました。
- すべての最終列を明示し、上流の列追加が出力契約を変えないようにしました。
- コメントは処理内容だけでなく、その粒度にする理由を記載しました。

## JOIN前集約

決済とレビューを `payment_order`、`review_order` で注文1行へ縮約してから注文カテゴリへ結合します。JOIN前に右側キーが一意であることが構造から読み取れます。明細は、明細指標用には明細のまま、注文系指標用には `order_category_item` へ集約して使い分けます。

## 同値性の確認方法

課題2の `fixed.sql` と課題3の `refactored.sql` をそれぞれ一時テーブルまたは一時ビューとして参照できる状態にし、次を確認します。

- 行数と出力キー重複数
- 列別NULL件数
- 件数・金額列のSUM、率・日数列のMINとMAX
- 文字列と日付を含む双方向の `MINUS`
- 小数列をROUNDした行単位比較、または絶対差の最大値

小数の演算順序により最下位桁が異なる可能性があります。業務上許容する桁または誤差を先に定め、差を無条件に無視しません。

## 実行効率への影響

生の明細×決済×レビューを作らないため、中間行数の爆発を避けられます。一方、`item_detail` を複数CTEから参照するため、Snowflakeの最適化結果とQuery Profileは確認対象です。SQLテキストだけで実行時間の改善を断定できません。

## 別の構成が成立する条件

CTEの統合や分割、命名、決済配賦の実装位置は別の形でも構いません。最終出力の列、粒度、NULL、指標定義が同じで、双方向差分とコントロールトータルに問題がなければ妥当な別解になり得ます。インデント変更だけでは、本課題の責務分離と保守性改善を満たしません。
